## S0 — 리포 세팅 + 물리 스파이크

**날짜:** 2026-07-20
**담당 역할 에이전트:** `gameplay-programmer`
**사용 도구:** Claude Code (Opus 4.8) / Chrome DevTools MCP (브라우저 실행 확인)

### 목표

화면에서 팽이 둘이 부딪히고 승부가 난다. 사람이 한 대를, 봇이 다른 한 대를 조작하고,
스핀아웃 또는 링아웃으로 승패가 결정되며 결과가 표시된다.

### 실제 받은 지시 (원문 요약 — 제약 C5 대응)

> 이번 작업: S0 (리포 세팅 + 물리 스파이크)
>
> 1. 리포 세팅 — Vite + 바닐라 TypeScript(프레임워크 금지), Canvas 2D, `npm i -D vite typescript`,
>    `git init` + `.gitignore`, `vite.config.ts` 의 base 는 `'./'`.
> 2. 물리 시뮬레이션 — 접시형 아레나(중심 방향으로 거리에 비례하는 가속, 벗어나면 링아웃),
>    회전력(Spin)=HP(시간·속도·충돌로 감소, 0이면 스핀아웃), 원-원 충돌(겹침 분리 + weight 기반 임펄스,
>    데미지 = 상대속도 × (공격자 attack / 방어자 weight)), 방향키 가속 + Space 대시 버스트,
>    스탯 4종(attack/weight/stamina/control) 기준값 각 50.
> 3. 구조 제약 (S3 네트워크가 의존) — 고정 타임스텝 1/60초 누산기, 시뮬과 렌더 분리,
>    시뮬은 순수(step(상태,입력)→상태, DOM/Canvas/Date.now()/Math.random() 금지, 난수는 시드 기반 PRNG 주입),
>    밸런스 상수는 `src/game/balance.ts` 한 파일에만, 연출 이벤트를 시뮬이 배열로 뱉고 렌더가 소비,
>    심사자가 전체 소스를 읽으므로(C2) 파일을 쪼개고 이름을 줄이지 말고 물리 수식에 한 줄 주석.
> 4. 봇 — 지금은 최소한(상대를 향해 이동 + 가끔 스킬), 단 인터페이스는 `botInput(state, index) → InputCmd` 로 분리.
> 5. 렌더 — 판독 가능한 수준까지만(아레나 동심원, 색과 모양 둘 다로 구분되는 팽이 2개, 스핀·스킬 게이지, 결과, 재시작).
>
> 금지: 자기긍정 표현 / 실행 확인 없는 완료 보고 / 시뮬 내 부작용 / 밸런스 상수 하드코딩 / 타입 에러 잔존.

### 생성 결과 (AI 초안)

파일 14개. 계층은 `engine`(고정 타임스텝·PRNG·벡터) / `game`(밸런스·타입·시뮬·상태·봇·입력) /
`render`(팔레트·연출 버퍼·렌더러) 로 분리됨.

지시된 구조 제약은 초안에서 대체로 반영됨:

- 고정 타임스텝 누산기 + 프레임당 최대 스텝 수 상한 (death spiral 방지)
- 시뮬 내 `Date.now()` / `Math.random()` / DOM 접근 없음. 시드는 `main.ts` 에서 주입
- 밸런스 상수 전량 `balance.ts` 집중
- 연출 이벤트 배열(`SimulationEvent[]`) → `render/effects.ts` 소비 구조
- `botInput(state, index) → InputCommand` 순수 함수. 봇은 상태를 전진시키지 않는
  스테이트리스 해시(`noiseFromSeed`)를 써서 결정론을 깨지 않음

초안 상태의 밸런스 초기값: 접시 가속 340 / 마찰 1.55 / 충돌 데미지 계수 0.019 / 회전력 자연감소 1.45.

### 사람이 고친 부분 + 고친 이유

AI 초안을 그대로 두지 않고, **헤드리스 스모크 테스트를 만들어 관측한 뒤** 다음을 수정했다.
아래 4건은 전부 "코드는 돌아가지만 게임으로서 성립하지 않는" 종류의 결함이다.

#### (1) 타입 에러 — `const` 좁히기가 클로저로 전파되지 않음

- **증상:** `npm run build` 에서 `'context' is possibly 'null'` 10건.
  `const context = canvas.getContext('2d'); if (!context) throw ...` 로 좁혔지만
  중첩 함수 안에서는 좁힘이 유지되지 않았다 (TypeScript 7.0.2 / tsgo).
- **수정:** 좁힌 값을 타입 주석이 붙은 새 `const` 에 재대입.
- **이유:** 지시상 타입 에러를 남긴 채 넘길 수 없다.

#### (2) 동일 스탯끼리 무승부가 25% 발생 — 충돌 데미지 모델이 대칭이었음

- **증상:** 초안은 충돌 시 양쪽에 **같은 데미지**를 넣었다.
  스탯이 같은 두 팽이는 회전력 곡선이 완전히 겹쳐 같은 스텝에 동시 사망 → 무승부.
  16회 중 4회(25%) 무승부 관측.
- **수정:** 충돌 법선 방향으로 더 많이 밀고 들어간 쪽을 **공격자**로 판정하고
  (임펄스 적용 *전* 속도로 판정해야 한다 — 적용 후에는 부호가 뒤집힌다),
  방어자는 정타, 공격자는 반동만 받도록 비대칭화. `COLLISION_ATTACKER_RECOIL_RATIO = 0.5` 신설.
- **이유:** 물리적으로도(파고든 쪽이 유리) 게임적으로도(선공 보상) 맞고, 무승부 비율이 16회 중 1회로 내려갔다.
- **관측:** 무승부 4/16 → 1/16.

#### (3) ★ 방향키를 한쪽으로 계속 누르면 스스로 링 밖으로 나감 — 접시 모델이 자력 추진을 못 막음

- **증상:** 브라우저에서 오른쪽 방향키를 계속 누르자 회전력 98을 남긴 채 약 1초 만에 링아웃.
  링아웃이 "강한 타격의 보상"이 아니라 "조작 실수 자폭"이 되어 접시 아레나 설계가 무의미해진다.
- **원인:** 지시받은 모델(중심 방향 가속이 거리에 **비례**)만으로는 복원력의 상한이 낮다.
  입력 가속 430 / 마찰 1.35 → 자력 최고속 약 318 유닛/초.
  반면 완만한 경사만으로 중심에서 탈출하는 데 필요한 속도는 약 198 유닛/초.
  즉 **자력 추진이 복원력을 항상 이긴다.**
- **수정:** 접시에 **테두리 턱(lip)** 추가. 거리비 0.72 바깥에서만 (초과분)² 에 비례하는
  추가 복원 가속(`DISH_LIP_ACCELERATION`)이 걸린다.
  지속적인 자력 추진은 못 넘고, 충돌·버스트로 순간적으로 실린 큰 속도는 넘을 수 있다.
- **이유:** 실제 베이스타디움의 형상(가운데는 완만하고 가장자리에 턱)과도 일치하고,
  "링아웃 = 순간적인 큰 임펄스의 결과"라는 의도를 물리로 강제한다.
- **검증:** 이 결함 전용 회귀 프로브를 `tools/headlessBattle.ts` 에 추가했다.
  - 자력 이탈 A(방향키만 15초): 링아웃 없음, 최대거리비 0.925 → 설계 요건 충족
  - 자력 이탈 B(방향키+버스트 15초): 링아웃 발생 → 게이지를 소모한 의도적 행동이므로 허용
  - 브라우저 재확인(61fps, 20초간 방향키 유지): 링아웃 없이 테두리에 눌린 채 회전력만 소모됨

#### (4) 밸런스 재조정 — 배틀이 11초 만에 끝나고 링아웃이 한 번도 안 나옴

- **증상:** 초안 수치로 봇 대 봇 배틀이 평균 약 11초에 종료, 8회 전부 스핀아웃, 링아웃 0회.
- **수정:** 충돌 데미지 계수 0.019 → 0.011, 회전력 자연감소 1.45 → 0.85,
  접시 가속 340 → 152, 마찰 1.55 → 1.35, 반발계수 0.86 → 0.95, 버스트 임펄스 300 → 360.
- **관측:** 배틀 길이 약 11초 → 약 17~26초. 링아웃은 버스트 사용 시 도달 가능함을 프로브로 확인.
- **미해결로 남김:** 아래 §미해결 참조.

### 미해결 (다음 담당에게 인계)

1. **링아웃이 움직이는 상대에게는 거의 안 난다.** 숙련 입력(무오차 조준 + 게이지 차면 즉시 버스트)
   대 봇 8회에서 전부 스핀아웃. 방어자가 맞은 직후 다시 안쪽으로 추진하기 때문에
   충돌로 얻은 바깥 방향 속도가 상쇄된다. 링아웃 발생률 목표치를 정하고 재조정할 것 — systems-designer.
2. **밸런스 수치 전부 미검증.** 손으로 맞춘 초기값이며 플레이 데이터 기반이 아니다.
3. **봇이 1스테이지 수준으로 약함.** 의도된 상태 — game-ai-engineer 가 고도화.
4. **렌더는 판독 가능 수준까지만.** 히트스톱·파티클·트레일 미구현 — technical-artist 가 담당.
   연결 지점은 `src/render/effects.ts` (시뮬이 뱉은 이벤트를 소비하는 곳).
5. **탭이 가려지면 게임 시간이 실제 시간보다 느리게 간다.** 프레임당 최대 스텝 수 상한의 의도된 결과이지만,
   S3 실시간 PvP 에서는 두 클라이언트의 틱이 벌어지는 원인이 된다. 네트워크 설계 시 다룰 것.

## 2026-07-20 — 파츠 12종 + 링아웃 레버 L1~L3 + 밸런스 검증 (systems-designer)

### 목표
S0 미해결 M1(링아웃 미발생)을 디렉터 판정(`02_게임설계.md §2`)에 맞춰 구현하고,
파츠 12종 테이블을 만들어 목표치 T1~T6 를 시뮬레이션으로 검증한다.

### 받은 지시 (요약)
- 디렉터 §3 확정 프레임 준수: 슬롯 3 × 4종 = 12종, 신규 스탯 금지, 넉백은 파생 합산값,
  특성 보유 파츠 최대 4종("기존 balance 상수 1개 × 배율 1개"), 등급·레어리티 없음
- 링아웃 레버 L1(넉백 임펄스)·L2(경직)·L3(턱 관통)을 **강타 판정 후 짧은 윈도우에서만** 작동하게 구현
- `tools/headlessBattle.ts` 를 확장해 T1~T6 자동 측정, 시드 고정 32판 이상
- 측정 → 조정 → 재측정 반복. 못 넣은 항목은 실패로 보고
- 구조 제약 유지: 고정 타임스텝, 시뮬 내 DOM/`Math.random()`/`Date.now()` 금지, 상수 하드코딩 금지

### 생성 결과 (AI)
- `src/game/parts.ts` 신규 — 파츠 12종 테이블 + 빌드 합산(`buildProfile`) + 아키타입 3종 정의
- `src/game/balance.ts` — 넉백 임계 2단계, 강타 임계 접근속도, L1~L3 파라미터 8종 추가
- `src/game/types.ts` — `BuildTuning`(특성 배율 4종), `KnockbackTier`, 경직·턱관통 잔여시간 필드
- `src/game/simulation.ts` — `applyKnockbackLevers` 신규, `applyInputs`(L2)·`applyDishSlope`(L3) 개입
- `tools/headlessBattle.ts` — T1~T8 자동 측정(시드 40 × 좌우 교대 = 매치업당 80판, 총 480판)

### 사람이 고친 부분 / 측정으로 뒤집은 부분

1. **L1 임펄스에 방어자 질량이 빠져 있었다.**
   AI 초안은 `defender.velocity += normal * impulseSpeed` 로 질량을 나누지 않았다.
   `types.ts` 는 weight 를 "충돌 시 밀림 저항"으로 정의해 두었는데 넉백에 대해서만 그 정의가 무효였다.
   측정으로 드러났다 — A2 스태미나 빌드가 링브레이커전 승률 22.5%.
   → `/ massMultiplier(defender.stats)` 추가. **이유:** 스탯 정의와 구현이 어긋나면
   플레이어가 스탯 설명을 읽고 세운 가설이 게임에서 배신당한다.

2. **AI 초기 레버 값이 링브레이커를 지배 빌드로 만들었다.** (T3 98.8%, T6 93.8%)
   원인은 임펄스를 넉백에 **선형 비례**로 준 것 — 넉백 18 이 임계1(6)의 3배가 됐다.
   → "임계1 기본값 58 + 초과분 1점당 2" 형태로 변경. **이유:** 임계1 을 살리면서 임계2 폭주를 막으려면
   두 구간을 따로 조절할 수 있어야 한다.

### ★ 측정 후 반려한 경로 — "빌드 스왑"(제출 #4 재료: 지우지 않는다)

착수 시 후반 구간 봇에게 **파츠 빌드**를 줘 강하게 만드는 경로(훅 3, `botBuildForTier`)를 먼저 시험했다.
tier3=어택 아키타입(L02/D02/R02), tier4=링브레이커(L04/D04/R04). 측정(기준=시작 빌드 플레이어, 80판):

| 구간 봇 빌드 | 기준(시작빌드) 플레이어 승률 |
|---|---|
| tier3 어택 아키타입 | **1.3%** (봇이 압살) |
| tier4 링브레이커 | **71.3%** (봇이 오히려 약함) |

**반려 사유 3건:**
1. **비단조.** 어택 빌드는 미투자 시작 빌드를 1.3% 로 짓밟는데, 링브레이커는 낮은 atk·sta 탓에 스핀전에서
   져 71.3% 로 약하다. 빌드 **파워 격차가 실력 격차를 압도**해 계단이 울퉁불퉁해진다(3구간이 4구간보다 어려움).
2. **디렉터 N6 위반.** §12-3/N6 은 "기존 5개 상수 조합만, 파라미터 커브로만" 난이도를 올리라 명시. 빌드 스왑은 다른 레버다.
3. **난이도 설계 원칙 위반 소지.** 봇에게 강한 빌드를 쥐여주는 것은 "스탯 뻥튀기"의 한 형태로 읽혀,
   플레이어가 치트로 느낄 위험이 있다.

→ 빌드 스왑을 제거하고 `botBuildForTier` 는 전 구간 시작 빌드로 고정(훅만 남김). 난이도는 **스킬 파라미터만으로** 만든다.
   (후반 봇 빌드 부여는 본선 에이전트 설계서에서 "플레이어 빌드 성장과의 균형"을 별도 측정한 뒤 재검토 대상.)

### 스킬 계단 튜닝 시행착오

**핵심 발견 1 — 동일 빌드에서 플레이어 승률은 실력 파리티 근처의 소프트 계단 함수다.**
봇이 플레이어보다 확실히 약하면(조준오차 큼) 동일 시작 빌드에서 플레이어가 ~95~100% 이긴다. 봇이 파리티를
넘어서야 승률이 급락한다. 그래서 파리티 아래 구간들(1·2)은 천장 근처에 몰리고, 실제 난이도 분화는 3·4구간에서 난다.
초기 튜닝은 100/96.3/77.5/33.8(1→2 거의 평평 + 3→4 절벽)이었다. 1구간을 더 무디게(조준 0.62·스로틀 0.78),
2구간을 살짝 조여(조준 0.23) 1→2 단차를 5pt 로 벌리고, 4구간을 조준 0.15 로 클라이맥스에 맞췄다.

**핵심 발견 2 — 완주율(T13)은 봇 강도가 아니라 3택1 픽 전략(빌드 설계)이 지배한다.**
같은 봇 티어에서 완주율이 **순진픽(항상 0번) 17.5% ↔ 전투력픽(빌드 파워 최대화) 77.5%** 로 벌어졌다.
순진픽은 음수 사이드그레이드를 집어 빌드가 정체·약화하고(ai-log gameplay-programmer 시행착오 4 와 동일 현상),
전투력픽은 빌드가 커져 시작 빌드 봇을 실력과 무관하게 압도한다. **즉 시작 빌드 봇 상대로는 플레이어의 성장한
빌드가 완주를 좌우하고 봇 스킬의 레버리지는 작다.** 목표 40~70% 는 이 두 극단 사이에 있어 "적당히 두는 보통
플레이어"면 달성 가능하나, 완주율 자체는 봇 튜닝만으로 목표에 못 박을 수 없다 — 픽/보상(N7)·빌드 밸런스 영역이다.

4. **동일 빌드 스킬 계단의 1→2 단차는 구조적으로 작다**(둘 다 파리티 아래). 승률만으론 티어 1·2 가 비슷해 보이나
   봇 **행동**(조준 정밀도·이동 속도·버스트 빈도)은 뚜렷이 다르다 — 심사자가 느끼는 난이도 신호는 승률만이 아니다.
5. **전 측정 봇 vs 봇(스크립트 플레이어).** 실제 사람 입력·자폭 이탈·브라우저 실플레이 미검증. 사람 확인은 gameplay-programmer 인계 절차와 동일.
6. **후반 봇 빌드 부여(반려 경로)** 는 본선 에이전트 설계서에서 플레이어 성장과의 균형을 별도 측정 후 재검토 대상.

## S2 §17 L0 — 파워 판타지: STRIKE 공격형 + 컨텍스트 분리 + 리롤/PvP 정규화

**날짜:** 2026-07-24
**담당 역할 에이전트:** `systems-designer`
**입력 고정:** N8=0.30/N9=0.6, 무세트 아키타입 파리티(②), BREAK sta+5, 링아웃 물리 전부 불변.

### 목표

PT-2 "뽕맛 부재"의 구조 진단(런=경쟁 밸런스 최적화) 대응(디렉터 6차 §17). L0: STRIKE 세트를
수비(sta+4)에서 **공격형(타격 데미지 배율)**으로, SET4′를 **런 해제/PvP 유지**로 분리, 리롤 N 권고,
★ 격납고 완주 빌드가 PvP 로 갈 때 강화 정규화 상한 명시.

### 구현 (SET3 준수 — 신규 효과 금지)

- STRIKE 세트 = 기존 데미지 계수(COLLISION_DAMAGE_PER_RELATIVE_SPEED) × 배율 1개.
  `BuildTuning.damageDealtMultiplier` 추가 → `applyCollisionDamage` 가 `source.tuning.damageDealtMultiplier` 곱.

### STRIKE 배율 스윕 시행착오 (PvP SET4′가 상한을 조인다)

STRIKE 배율은 런 압도(강화가 주 견인)엔 여유가 크나, **PvP 완성끼리 SET4′(≤75%)가 상한을 조인다:**

| STRIKE 배율 | PvP STRIKE vs GUARD | 런 T-RUN1(vs 1구간) | 런 T-RUN2(vs 4구간) |
|---|---|---|---|
| ×1.35 | 77.5% ★초과 | 100% | 100% |
| ×1.30 | 75.0% 경계무마진 | 100% | 100% |
| **×1.25 (확정)** | **66.3% 마진** | **100%** | **100%** |
| ×1.20 | 57.5% | 100% | 100% |

- **핵심 발견 1 — 런 압도는 STRIKE 배율이 아니라 강화가 견인.** 배율을 ×1.20~1.35 어디로 놔도 T-RUN1 100%.
  따라서 배율은 **PvP SET4′ 제약(≤75%, F-6 마진 ~72)**만 보고 정하면 된다 → ×1.25(66.3%).
- **핵심 발견 2 — T-RUN2 파리티가 배율·강화로 안 잡힌다.** +3(atk90)에서 이미 4구간 봇 100% 압도. 강화 상한을
  낮춰도(+3) 파리티 안 됨. **봇 4구간이 완성 빌드를 못 따라잡는 게 원인**(game-ai-engineer 17-F-3).
  → 강화 런 상향(+5)은 파워 증분 없이 판만 8s 로 단축(§17-C 제약 위반) → 유효 상한 +3 권고(U17).
- **핵심 발견 3 — T4 무관용은 안전.** STRIKE 데미지 배율은 이동에 무영향 → 방향키만 자력 이탈 0건 유지.
  T-RUN 의 자력이탈(+5 1건)은 버스트 유래(PM 수용). 배율이 T4 를 깰 경로 없음.

## S3 공개 relay build 환경 경계 (Codex)

**날짜:** 2026-07-27

### 관측과 수정
- placeholder `VITE_RELAY_URL=wss://relay.example`로 `npm run build`를 실행했을 때 bundle에 endpoint가 없었다. build 산출물은 `import.meta.env?.VITE_RELAY_URL`을 그대로 남겼다.
- 원인 가설: Vite의 정적 치환은 direct `import.meta.env.VITE_RELAY_URL` expression을 대상으로 하며 optional chaining이 든 경로는 치환하지 않는다.
- `tools/relayBuild.mjs`를 먼저 추가했다. 초기 실행은 Windows `npx.cmd` spawn과 file URL 경로 처리에서 멈췄고, `process.execPath` + `fileURLToPath`으로 test runner만 수정했다. 그 뒤 expected failure는 `VITE_RELAY_URL was not embedded in the production bundle`이었다.
- `src/main.ts`를 direct expression으로 바꾸고 `src/vite-env.d.ts`에서 local `ImportMetaEnv` type을 선언했다. `node tools/relayBuild.mjs`는 `Relay build configuration cases: 1/1 observed`를 출력했다.
- GitHub Actions Build step에는 `VITE_RELAY_URL: ${{ vars.VITE_RELAY_URL }}`를 넣었다. 값이 없는 경우 빈 값으로 build되고 기존 Pages 대기실 문구가 유지된다.

2. Pages 공개 build의 Worker WebSocket과 Canvas 두 브라우저 입력은 사람 시험이 필요하다.

## S3 모바일 버스트 방향 스냅샷 (Codex)

**날짜:** 2026-07-28
**담당:** Codex
**근거:** PM의 모바일 관찰: 터치에서 선택한 방향과 다른 쪽으로 버스트가 나가는 듯하며 조작이 불안정함.

### 목표
버스트 버튼의 pointerdown과 다음 60Hz simulation tick 사이에 이동 스틱이 바뀌어도, 탭 시점의 터치 방향으로 해당 버스트를 처리한다. 다음 tick의 일반 이동은 최신 스틱 방향을 유지한다.

### 원인 추적과 red 관측
- 기존 `src/app/touchInput.ts`의 `handleBurst`는 `burstQueued = true`만 남겼다. `consumeCommand()`는 다음 tick의 현재 `moveX/moveY`를 반환했다.
- `tools/touchInput.ts`에 오른쪽 스틱→버스트 탭→왼쪽 스틱 이동을 같은 tick 이전에 만드는 사례를 추가했다. 변경 전 `npm run smoke:touch-input`은 `burst must use the held direction at button press even when the stick moves before the next tick` 오류로 종료 코드 1이었다.

### 코드와 관측
- `handleBurst`가 탭 시점의 `moveX/moveY`를 저장한다. `consumeCommand()`은 burst가 큐에 있을 때만 저장 방향을 반환하고 즉시 초기화한다. 다음 tick은 최신 스틱 방향을 반환한다.
- `src/game/simulation.ts`의 버스트 방향 규칙은 수정하지 않았다. 전달된 입력이 0일 때 속도 방향으로 fallback하는 기존 규칙도 유지한다.
- `npm run smoke:touch-input` → `Touch input cases: 19/19 observed`; `npm run build` → 종료 코드 0; `npm run smoke:run` → 동일 시드 8/8 일치 (2026-07-28 콘솔 측정).

### 미해결 / 다음 인계
1. 충돌이나 큰 역방향 관성이 버스트 임펄스보다 큰 경우 실제 궤적은 입력과 달라질 수 있다. 이 작업은 터치 event↔fixed tick 경계만 바꿨으므로, 해당 사례는 `[UNSUPPORTED]`이며 별도 물리 재현이 필요하다.
2. 실제 모바일에서 오른쪽 홀드→버스트 탭→손가락 이동을 여러 번 시험한 감각은 자동 smoke로 관측하지 못했다. 공개 Pages에 `ec1100c`를 push한 뒤 사람 기기에서 재확인한다.
